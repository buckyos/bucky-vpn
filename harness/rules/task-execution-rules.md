# Task Execution Rules

## Authority
- Current-user confirmation of the displayed proposal and tier under [Task Entry Gate Rules](task-entry-gate-rules.md) authorizes the entire confirmed task: artifacts, implementation, verification, independent review, corrections, and closeout. No extra mode, launch instruction, or stage approval is needed.
- Record the actual confirmation and approve the proposal. File presence, unrelated approval, and silence do not authorize a new task. Honor later pause, stop, or scope-narrowing instructions.

## Execution
- Standard uses the [lighter flow](task-entry-gate-rules.md#tier-default-flows). High-risk uses proposal → design → implementation → testing → acceptance, with `design.md`, `testplan.yaml`, optional `testing.md`, and durable `lifecycle.json` receipts.
- After a high-risk stage returns its artifacts and required evidence, the parent runs `task-transition.py advance` to execute completion checks once, approve completed design/testing documents, bind receipts to their content, and advance. Proposal approval remains the user's decision. Dispatch the next stage only after the transition succeeds.
- Review and complete solutions already present in the proposal under the design/test owners' handoff guidance: preserve sound decisions, fix defects, fill gaps, and implement/run required tests.
- Follow design dependencies. Delegate when [session context needs renewal](#standard-task-session-context) and for [independent acceptance](#high-risk-stage-subtasks); otherwise reuse an execution agent with enough context capacity. Use the generated AGENTS step-to-agent mapping for responsibilities.
- Finish high-risk work only after independent acceptance succeeds, `task-transition.py complete` records acceptance, and `task-index.py remove` closes the task. Process checks do not substitute for delivery.

## Subagent Context
- Every subagent MUST start without inheriting its parent's conversation history, regardless of tier, stage, re-entry, or delegation depth. When using `spawn_agent`, explicitly set `fork_turns: "none"`; do not omit the parameter or use `"all"`. With other delegation tools, select the equivalent no-history setting.
- Provide a concise task-specific handoff and references to governing repository sources. Do not paste the full conversation or tool-output history into the handoff. Standard and high-risk handoff contents are defined below; apply the same principle to optional and nested subtasks.

## Standard Task Session Context
- At execution start and before each subsequent work step, assess the current session's accumulated information. If it already contains substantial information, a `standard` task MUST create a fresh subagent task for the remaining execution work before proceeding, even when the delivery is simple or small. A checklist item alone is not a subagent task.
- Treat extensive prior-task history, long investigation/log/tool output, repeated requirement discussions, or context compaction/pressure as signals of substantial session information. Do not wait for the context limit or require an exact token count to apply this rule.
- Apply [Subagent Context](#subagent-context) and provide a concise handoff: confirmed intent and scope, canonical packet/task bindings, applicable rules, relevant source paths, verified findings, completed work, pending work, and done criteria. Derive its role from the generated AGENTS mapping.
- The parent coordinates communication, shared task records, handoffs, and closeout; the subagent executes the delegated work and returns artifacts, verification evidence, findings, and unresolved questions. Preserve dependencies and independent completion review.
- Reuse the same packet, task identity, and linked change record. Delegation retains the standard flow and gates; it does not upgrade the tier or create high-risk stage artifacts. If the execution session later accumulates substantial information, hand off the remaining work to another fresh subagent.
- If required subagent execution is unavailable, report the blocker and preserve unfinished state. Do not continue the delegated execution work in the crowded parent session.

## High-Risk Stage Subtasks
- Proposal, design, implementation, and testing MAY run in the parent or reuse an execution subagent across stages when context capacity is sufficient. Assess context at each stage entry and return; use the context-pressure signals and concise handoff in [Standard Task Session Context](#standard-task-session-context) when renewal is needed. Stage changes alone do not require a new agent.
- After final high-risk confirmation, the proposal owner completes the required risk profile and proposal metadata before advancement to design. Record the reason for these updates and retain the approval bound to unchanged confirmed intent. If review changes requirements, scope, or acceptance boundaries, or raises an unresolved user decision, return the proposal to draft and reconfirm under Task Entry Gate Rules before downstream execution.
- The parent owns orchestration, user communication/confirmation, shared task registration, approval records, lifecycle transitions, and index closeout. Each stage owner produces its artifacts and required evidence, including pre-edit checks and test/verification runs. Delegated owners return evidence, findings, unresolved questions, and the proposed next action; they MUST NOT run completion profiles or lifecycle transitions. The parent validates the stage result, then runs `task-transition.py advance` (or `complete` for accepted acceptance); that command owns completion checks, receipt recording, and advancement/closeout. Do not run a separate `harness-check.py --profile completion` before the transition. Failed completion defaults to correction by the same stage owner before retry.
- Apply [Subagent Context](#subagent-context) and give each subagent the canonical packet path, `version`, module/target modules, `change_id` values, active stage/tier, relevant proposal/design/test sources, routed rules, prior evidence, and stage done criteria. All stage subtasks share the same packet and task identity; do not allocate a new packet or unfinished-index entry for each stage.
- Derive each owner's role from the generated AGENTS mapping; a `default` role may execute in the parent. Execute dependent stages sequentially and retain every stage check even when reusing an agent. Parallel work is limited to independent steps within the active stage and retains the owner's integration responsibility.
- Same-stage corrections and returns default to the original execution agent while context capacity permits. Acceptance MUST use a separate subagent that did not implement or test the delivery. Reuse that independent reviewer for follow-up while it remains independent and has sufficient context; supply current primary sources without treating prior pass conclusions as correctness evidence.
- If required context renewal or independent acceptance cannot run, report the blocker and preserve unfinished state. Optional execution delegation is not a prerequisite.

## Corrections and Stops
- Correct in-scope defects without another approval. Choose the impact-based correction flow below. Material corrections use `task-transition.py return --to <proposal|design|implementation|testing>` for the current or an earlier responsible stage; forward jumps are rejected. Acceptance first records `needs changes`. Retry invalidated checks and independent acceptance.
- Classify the correction by its consequences before invalidating evidence. Behavior, interface, state/ownership, validation semantics, or requirement changes use `return --to` for the earliest affected stage; clear its dependent receipts and reset affected approvals. Preserve unrelated valid evidence and historical findings. Requirement changes return to proposal for reconfirmation.
- Pure explanatory corrections to completed `design.md` or optional `testing.md` use `task-transition.py refresh-documentation --stage <design|testing> --reason <impact assessment> --review-evidence <consistency review>`. Keep the current stage and unaffected implementation/testing receipts; rerun document checks and independent consistency review only. The command renews content bindings and invalidates the acceptance conclusion. It does not authorize changed requirements, interfaces, behavior, risk decisions, test plans, assertions, test code, or runtime inputs. Uncertain impact uses the normal return flow.
- `return --to proposal` also sets `workflow_tier: pending`. Record the requirement revision, display and reconfirm the proposal/tier, then record the confirmed tier and approve the proposal under Task Entry Gate Rules. Resume with `task-transition.py advance`; never reuse old downstream receipts or approve the proposal automatically.
- Record returned issues and iterations in acceptance evidence. Stop and report after more than 5 unsuccessful iterations of the same issue.
- Requirement decisions or material scope changes need a blocking requirement finding, `rejected` report when acceptance is active, and revised proposal confirmation.
- Keep required evidence, tests, scope checks, and acceptance gates. If an external prerequisite blocks progress, report the concrete blocker and preserve unfinished-task state.
