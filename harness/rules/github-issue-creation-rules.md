# GitHub Issue Submission and Reply Rules

Applies whenever a task involves creating/submitting a GitHub issue or posting a reply/comment to an existing issue, in every tier and stage, including progress updates and completion reports. Before any GitHub create or comment call, the current user MUST explicitly confirm the exact final content. Drafting is preparation and does not authorize submission.

## Confirmation and Submission
1. Prepare and display the exact final submission:
   - New issue: target owner/repository, title, complete body, and all submission metadata (labels, assignees, milestone, project placement, etc.; use `none` where absent).
   - Reply/comment: target owner/repository, issue number and URL, complete reply body, and any submission metadata (`none` where absent).
2. Ask for explicit current-user confirmation and wait. Never submit in the turn that first displays a new or revised draft, even if the user requested immediate submission or skipped review.
3. Accept only unambiguous approval of that displayed submission. Silence, inferred intent, the original creation or reply request, proposal approval, another artifact's approval, agents, automation, and prior conversations do not count.
4. Any field change invalidates confirmation: display the complete revised draft and obtain confirmation again.
5. Submit exactly the confirmed content and metadata to the confirmed destination, then report the issue number and issue/comment URL. On failure, report it; do not silently alter the draft for a retry.

Confirmation covers one issue submission or one reply only. Multiple issues need separate complete drafts and confirmations; each reply also needs its own complete draft and confirmation, even if creating the issue or posting an earlier reply was already approved. Clarification and draft review do not authorize submission.
