# 模块分级矩阵

## 目标
- 为不同模块定义适合的协作自治级别、证据要求和评审关注点

## 分级定义
| Tier | 含义 | 默认自治度 | 最低要求 |
|------|------|------------|----------|
| A | 共享合同/高耦合核心模块 | 低 | 必须有直接 proposal/design/testing 覆盖，重点审查跨模块影响 |
| B | 运行时装配模块 | 中 | 必须遵守完整 stage 门禁，并补齐受影响子系统的验证说明 |
| C | 表现层或相对独立的适配层 | 中高 | 仍需模块 packet，但允许更聚焦的局部验证和更快迭代 |

## 模块映射
| 模块 | Tier | 原因 | 默认贡献模式 | 额外要求 |
|------|------|------|--------------|----------|
| `vpn-frame` | A | 客户端与服务端共享协议类型和运行时逻辑，合同漂移会同时影响两端 | `human-agent loop` for implementation, `agent-human loop` for upstream docs | 命中共享合同改动时必须声明 client/server 双边影响 |
| `bucky-vpn` | B | 客户端装配层，依赖共享协议且包含平台行为 | `human-agent loop` | 客户端本地 API、配置和打包影响要在 testing 中显式覆盖 |
| `bucky-vpn-server` | B | 服务端装配层，涉及存储、运行时和 API | `human-agent loop` | 存储/API 影响要在 testing 中声明验证边界 |
| `vpn_web` | C | Web 前端相对独立，但受后端合同和生成模型约束 | `human-agent loop` | 遵守前端不新增测试例外；模型形状变化时同步生成规则与验证说明 |

## 评审优先级
- Tier A：先看合同、边界和邻接模块影响，再看具体实现
- Tier B：先看 stage 文档与实现是否一致，再看运行时或治理接线
- Tier C：先看接口对齐和生成物约束，再看局部 UI/前端实现
